## Scope

This baseline uses the existing four-layer Qwen3.5 MoE fixture with adjacent full-attention and recurrent layers at the pipeline boundary. It runs on two Tesla T4 devices with ordinary host-sampled, single-sequence decode. The tested migration position is token position 5.

The measurements separate:

- KV allocation capacity from KV rows that contain live sequence data.
- recurrent-state bytes from KV bytes.
- state-copy time from allocation and preparation time.
- scheduler reserve work into setup, graph input preparation, graph construction, validation graph construction, and backend planning or allocation.
- CUDA Graph direct execution, warmup, capture, update, instantiation, launch, reset, and eviction activity.

`fused_probe_us` is an outer envelope. During initial context setup it can overlap the graph-input, graph-build, and backend-plan counters generated by the probe calls. Post-migration reserve does not rerun the probes in this fixture, so the measured migration breakdown does not contain that overlap.

## Synchronous event timeline

The current path has no background queue or independent completion event. Its measured ordering is:

1. Token position 4 completes and the host requests migration at frontier 5.
2. The shared scheduler synchronizes.
3. Destination state storage is allocated and each full tensor is copied.
4. Active layer and state pointers are swapped and the placement epoch advances.
5. Three primary reserve graphs and three validation graphs are built and planned.
6. Migration returns to the caller.
7. Token position 5 is submitted and completes.

For the representative mixed run, steps 2 through 6 took 3.597 ms and the request-to-next-token-complete interval was 5.350 ms. The copy counter records time spent in the current blocking backend copy API. S3 needs separate source-ready and destination-ready events before it can claim actual overlap.

## Current invalidation and rejection matrix

The experimental path currently rejects or invalidates the following cases:

| Operation or configuration | Current behavior | Future action |
| --- | --- | --- |
| more than one sequence or recurrent rollback snapshots | context construction rejected | keep out of first version |
| non-Qwen hybrid architecture, non-layer split, tensor overrides, vocab-only, no-alloc, or non-default context | context construction rejected | keep out of first version |
| context shift or sequence add/remove/copy/keep/divide | append-only state becomes false or shifting is disabled; migration rejected | cancel candidate and require a new sequence epoch |
| runtime LoRA or control-vector change | rejected with experimental placement | cancel or rebuild all signatures before later support |
| backend sampling, speculative/next-token embeddings, optimizer context | rejected by placement or migration guards | keep out of first version |
| second active context on the model | rejected by the model context guard | use private execution views, not a second public context |
| replica preparation while a context is active | rejected | finish weight preparation before context construction |
| same-device move, non-contiguous move, multi-stage interval, non-adjacent destination, or unvalidated layout | migration rejected | candidate whitelist remains explicit |
| placement epoch or active-layer identity change | previous logical graph reuse rejected | S2 needs an explicit runtime signature, not removal of the check |
| ubatch shape, output count, sampler set, attention mask shape, or memory input incompatibility | graph input reuse rejected | candidate runtime reports a cold miss |
| scheduler reset/reserve | previous host graph dependencies are released | invalidate native readiness for that runtime |
| bank allocation replacement or address generation change | not represented separately today | S1 adds bank generation and S2 includes it in the signature |

The existing PP regression covers same-device and multi-stage rejection, post-switch failure rollback, append-only mutation rejection, weight binding, state-device ownership, and continued inference after rollback. Async completion reorder, cancellation, stale events, journal overflow, and CUDA Graph eviction remain future-stage tests because those mechanisms do not exist yet.

## CUDA Graph finding

Immediately after each migration, both CUDA backends contained enabled graph records, but none were warm or executable for the new decode topology. The first and next decode each performed two direct CUDA evaluations. No capture, executable update, or graph launch occurred in those two steps.

This behavior follows the current CUDA Graph state machine: a stable graph key must be observed repeatedly before warmup completes and capture begins. A migration-time warmup therefore needs a persistent candidate runtime and stable tensor addresses. Copying state asynchronously into a temporary allocation cannot warm the graph that the promoted placement will later use.

## S0 conclusion

The implementation order should be:

1. Add fixed-address state banks and independent mutable metadata views.
2. Add a persistent candidate scheduler and graph runtime for each supported placement.
3. Move checkpoint copies to asynchronous streams and track completion by frontier.
4. Add exact replay or shadow catch-up using the candidate metadata view.
5. Warm the candidate CUDA Graph before promotion.
6. Promote by selecting already-ready banks and runtime state.

Optimizing state-copy bandwidth before steps 1 and 2 would not remove the dominant pause in this baseline.
